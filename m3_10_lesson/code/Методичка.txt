Структура JWT токена
1) Header
HS256 - симметричное шифрование (используется 1 ключ)
RS256 - асимметричное шифрование

2) Payload - полезная нагрузка, которая содержит данные на основе которых м/с предоставляет доступ.
Payload состоит из claims:
- sub : назнчение токена
- aud : аудитория для которой предназначен токен
- exp : срок жизни токена
- iat : время создания токена

Кроме служебных claims можно делать свои.

Но чем больше claims, тем медленнее это будет работать.

Не стоит хранить в claims какие-нибудь важные данные, например, номер паспорта. Их могут перехватить.

3) Signature - подпись, которая генерируется следующим образом:
 Закодированные в base64 заголовок и полезная нагрузка объединяются через точку. Результат данного
 хэширования это подпись


 Итого

 Заголовок и payload хешируются и объединяются в одну строку.
 И эта строка становится токеном, которая используется для аутентификации при передаче данных.

 Мы получили захешированные эти два элемента и к ним применяется алгоритм, указанные в Header.
 И все это вместе и есть наша подпись.


 Возникает вопрос, как микросервисы проверяют JSON токен на то, что он корректный.
 Все наши микросервисы знают единый секретный ключ (из header), который используется для подписи токенов.


 Зачем нужна подпись?

 Если в хедере не будет написано значение ключа alg (none), то возникает риск утечки данных из payload.

 Основные преимущества JWT:

 GWT токен хранится на стороне клиента не просто в куках, а с параметрами (secure например).

 Также для безопасности нужно использовать https, чтобы не было перехвата токена.

 У coocki можно также поставить параметр http-only.

Но даже используя эти методы, риск все равно остается. И чтобы его минимизировать,

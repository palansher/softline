# Сравнение PostgreSQL и MongoDB

Использование PostgreSQL с типом данных **`jsonb`** вместо MongoDB — это сегодня отраслевой стандарт для большинства проектов. В 80–90% случаев PostgreSQL полностью закрывает потребности NoSQL-документоориентированного хранилища, избавляя от необходимости поддерживать отдельную базу данных.

---

## Сравнение PostgreSQL (JSONB) и MongoDB

| Критерий | PostgreSQL (`jsonb`) | MongoDB |
| --- | --- | --- |
| **Модель данных** | **Гибридная** (SQL + Document) | **Документная** (BSON) |
| **Транзакции (ACID)** | Полноценная поддержка из коробки для всей БД | Есть (с v4.0), но сложнее в эксплуатации |
| **Индексация JSON** | Мощные индексы **GIN**, B-tree, выражение/частичные индексы | Multikey, Compound, Text, Geospatial |
| **Масштабирование** | Преимущественно **вертикальное** (для горизонтального шардинга нужен Citus) | Нативный **горизонтальный шардинг** «из коробки» |
| **Типы данных внутри** | Стандартный JSON (строки, числа, булевы, массивы, объекты) | **BSON** (поддерживает `Date`, `ObjectId`, `Decimal128` и др.) |
| **Операционная сложность** | **Низкая** (одна универсальная БД) | **Средняя/Высокая** (при настройке реплик и шардов) |

## Главные преимущества PostgreSQL `jsonb`

### 1. Гибридный подход

Вы можете сочетать строгую реляционную схему там, где нужна надежность (пользователи, биллинг, заказы), и гибкий `jsonb` там, где структура часто меняется (настройки, логи, свойства товаров, интеграции с внешними API).

```sql
-- Таблица с обычными колонками и гибким JSONB
CREATE TABLE products (
    id BIGSERIAL PRIMARY KEY,
    sku VARCHAR(50) UNIQUE NOT NULL,
    price NUMERIC(10, 2) NOT NULL,
    attributes JSONB NOT NULL DEFAULT '{}'::jsonb
);

```

### 2. Полноценный ACID для смешанных данных

Вы можете в рамках единой транзакции обновить и классическое SQL-поле, и значение глубоко внутри JSONB-документа. Если произойдет сбой, откатится всё.

### 3. Эффективная индексация (GIN)

GIST/GIN-индексы позволяют быстро искать по любым ключам и значениям внутри `jsonb`.

```sql
-- Индексация всего JSONB-документа
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);

-- Поиск товара, у которого color = 'red' и brand = 'Apple'
SELECT * FROM products 
WHERE attributes @> '{"color": "red", "brand": "Apple"}';

```

Если вам нужен поиск только по конкретному полю внутри JSONB, можно создать классический B-Tree индекс по выражению:

```sql
CREATE INDEX idx_user_email ON users (((profile->>'email')));

```

## Когда MongoDB всё ещё предпочтительнее?

1. **Огромные объемы и горизонтальное масштабирование (Write-heavy):** Если у вас терабайты данных в секунду и необходим распределенный шардинг «из коробки» без сторонних расширений.
2. **Специфические типы данных BSON:** Если вам принципиальна нативная поддержка `ObjectId`, бинарных данных или специфических дат непосредственно на уровне формата хранения (в PG даты внутри JSONB хранятся как ISO-строки).
3. **Строгая ориентация команды на Document API:** Если разработчики привыкли использовать MongoDB aggregation pipeline, Mongoose и не хотят писать SQL/JSON-операторы PostgreSQL.

## Как выглядит работа с JSONB в PostgreSQL

* **Извлечение значения:** `profile->>'name'` (возвращает `text`) или `profile->'age'` (возвращает `jsonb`).
* **Проверка наличия ключа:** `profile ? 'email'`
* **Проверка подмножества (Inclusion):** `profile @> '{"role": "admin"}'`
* **Изменение значения:** `JSONB_SET(profile, '{address,city}', '"Berlin"')`
* **JSON Path (SQL/JSON):** Позволяет делать сложные выборки через `jsonb_path_query`.

---

## Вердикт

Если у вас **уже есть PostgreSQL** или вы создаете новый стандартный веб/мобильный проект — **начинайте с PostgreSQL (`jsonb`)**. Переход на отдельную NoSQL БД оправдан только тогда, когда вы упретесь в физические лимиты одной машины по записи или вам потребуется специфичный функционал MongoDB.

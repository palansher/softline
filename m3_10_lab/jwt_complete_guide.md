# Подробное руководство по JSON Web Token (JWT)

> **Цель методички:** Понять устройство, принцип работы, сферы применения и правила безопасности при использовании JWT-токенов в веб-разработке и микросервисной архитектуре.

---

## 1. Введение: Что такое JWT и зачем он нужен?

**JWT (JSON Web Token)** — это открытый стандарт ([RFC 7519](https://tools.ietf.org/html/rfc7519)) для безопасной передачи информации между двумя сторонами в виде JSON-объекта. Информация в токене заверенa **цифровой подписью**, что позволяет проверять её подлинность и неизменность.

### Главная проблема, которую решает JWT

В традиционной **сессионной аутентификации** (Stateful):

1. Пользователь логинится.
2. Сервер создает сессию в базе данных или RAM (Redis) и отправляет клиенту `Session ID` в Cookie.
3. При каждом запросе сервер ищет `Session ID` в базе, чтобы понять, кто делает запрос.
*Минус:* При масштабировании на десятки микросервисов всем сервисам приходится постоянно обращаться к единой базе сессий.

В **JWT-аутентификации** (Stateless):

1. Пользователь логинится.
2. Сервер выдаёт signed JWT, содержащий ID пользователя и его роли.
3. Клиент сохраняет токен и отправляет его при каждом запросе.
4. Сервер (или любой микросервис) **не обращается к базе данных**, а просто проверяет цифровую подпись токена своими математическими ключами.

---

## 2. Развеиваем Главные Заблуждения (Важно!)

Перед разбором структуры важно уяснить три принципиальных момента:

1. **JWT — это НЕ шифрование, это ПОДПИСЬ!**
   * Данные внутри JWT **закодированы** (Base64URL), а **не зашифрованы**. Любой человек, перехвативший токен, может декодировать его и прочитать содержимое (например, на сайте [jwt.io](https://jwt.io)).
   * Подпись гарантирует **целостность** (что данные не подменили), но **не конфиденциальность** (данные видны всем).

2. **Нельзя хранить в JWT секретные данные!**
   * Пароли, номера паспортов, банковские карты, персональные данные **категорически нельзя** помещать в JWT.

3. **Размер имеет значение**
   * JWT передается в заголовке `Authorization` каждого HTTP-запроса. Чем больше данных вы туда положите, тем больше сетевого трафика будет расходоваться на каждый запрос.

## 3. Анатомия JWT-токена

JWT состоит из трёх частей, разделённых точками (`.`):

```
HEADER.PAYLOAD.SIGNATURE
```

Пример готового токена:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFsZXgiLCJyb2xlIjoiYWRtaW4iLCJpYXQiOjE1MTYyMzkwMjIsImV4cCI6MTUxNjI0MjYyMn0.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

Разберем каждую часть подробно.

---

### Часть 1: Header (Заголовок)

Содержит метаданные о самом токене: используемый алгоритм подписи и тип токена.

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

* `alg` (*Algorithm*) — алгоритм для создания цифровой подписи (например, `HS256`, `RS256`).
* `typ` (*Type*) — тип токена, всегда `"JWT"`.

---

### Часть 2: Payload (Полезная нагрузка)

Содержит **Claims** (заявления/утверждения) — данные о пользователе и служебные поля.

Claims делятся на три категории:

1. **Зарегистрированные (Registered claims):** Стандартные зарезервированные ключи (все ключи из 3 букв для экономии места):
   * `sub` (*Subject*) — субъект токена (обычно ID пользователя, например, `"user_12345"`).
   * `iss` (*Issuer*) — кто выдал токен (например, `"https://auth.mysite.com"`).
   * `aud` (*Audience*) — для кого предназначен токен (например, `"https://api.mysite.com"`).
   * `exp` (*Expiration Time*) — время окончания действия токена в Unix Timestamp (например, `1700000000`). **Обязательное поле!**
   * `nbf` (*Not Before*) — время, до наступления которого токен недействителен.
   * `iat` (*Issued At*) — время создания токена.
   * `jti` (*JWT ID*) — уникальный идентификатор токена (для предотвращения повторного использования/Replay-атак).

2. **Публичные / Пользовательские (Custom claims):** Ваши собственные данные, необходимые микросервисам для работы:

   ```json
   {
     "sub": "usr_9981",
     "iss": "auth.company.com",
     "exp": 1723320000,
     "iat": 1723316400,
     "name": "Иван Иванов",
     "role": "admin",
     "email": "ivan@company.com"
   }
   ```

---

### Часть 3: Signature (Цифровая подпись)

Подпись позволяет проверить, что токен не был изменен после создания.

#### Как формируется подпись (Пошагово)

1. **Base64URL-кодирование Header:**
   `encodedHeader = base64urlEncode(Header)`
2. **Base64URL-кодирование Payload:**
   `encodedPayload = base64urlEncode(Payload)`
3. **Объединение через точку:**
   `dataToSign = encodedHeader + "." + encodedPayload`
4. **Применение алгоритма с использованием секретного ключа:**
   `signature = HMACSHA256(dataToSign, secret_key)`
5. **Кодирование подписи в Base64URL:**
   `encodedSignature = base64urlEncode(signature)`

#### Финальная сборка токена

```text
JWT = encodedHeader + "." + encodedPayload + "." + encodedSignature
```

Если злоумышленник попытается изменить `role` в Payload с `"user"` на `"admin"`, строка `encodedPayload` изменится. При проверке микросервис пересчитает подпись со своим секретным ключом — значение подписи **не совпадет**, и токен будет отклонен!

## 4. Алгоритмы подписи: HS256 vs RS256

Это фундаментальный вопрос построения микросервисной архитектуры.

| Критерий | HS256 (HMAC with SHA-256) | RS256 (RSA with SHA-256) |
| :--- | :--- | :--- |
| **Тип шифрования/подписи** | Симметричный | Асимметричный |
| **Ключи** | **Один секретный ключ** (Secret Key) для подписи и проверки | **Пара ключей:** Private Key (закрытый) и Public Key (открытый) |
| **Кто подписывает?** | Сервис аутентификации | Сервис аутентификации (используя Private Key) |
| **Кто проверяет?** | Все микросервисы (должны знать секретный ключ) | Все микросервисы (знают только Public Key) |
| **Уровень безопасности** | Если компрометирован один микросервис — скомпрометирована вся система (он может генерировать поддельные токены). | Высокий. Микросервисы имеют только Public Key, генерировать токены они **не могут**. |
| **Скорость работы** | Очень высокая | Чуть медленнее, но надежнее |

### Схема проверки в микросервисах с RS256

```text
 +-------------------+           1. Логин            +-------------------+
 |   Пользователь    | ----------------------------> |   Auth Service    |
 |     (Клиент)      | <---------------------------- | (Has Private Key) |
 +-------------------+    2. Выдает JWT (RS256)      +-------------------+
           |                                                   |
           | 3. Запрос с JWT                                   | 4. Раздает Public Key
           v                                                   v
 +-----------------------------------------------------------------------+
 |                  Микросервисы (Order, Billing, User)                  |
 |  Проверяют подпись JWT с помощью Public Key (JWKS / Endpoint)        |
 +-----------------------------------------------------------------------+
```

## 5. Разбор Уязвимости `alg: "none"`

В спецификации JWT существует специальный режим без подписи — `alg: "none"`.

* **В чем суть уязвимости?**
  Если библиотека валидации токенов на сервере настроена некорректно, злоумышленник может отправить токен с `Header: {"alg": "none", "typ": "JWT"}` и пустой третьей частью (`Header.Payload.`).
  Если сервер «слепо» доверяет полю `alg` из хедера, он пропустит токен **без проверки подписи**, позволив хакеру подделать любую роль или ID пользователя.

* **Как защититься?**
  На стороне сервера необходимо **явно указывать ожидаемый алгоритм** при валидации (например, жестко задать `algorithms=["HS256"]` или `["RS256"]`), а не считывать его бездумно из Header пришедшего токена.

## 6. Где хранить и как передавать JWT на клиенте?

### Способ передачи

Токен передается в HTTP-заголовке `Authorization` при каждом запросе:

```http
Authorization: Bearer <your_jwt_token_here>
```

### Сравнение мест хранения на стороне клиента

| Место хранения | Плюсы | Минусы | Защита |
| :--- | :--- | :--- | :--- |
| **LocalStorage / SessionStorage** | Легко доступен из JavaScript (SPA, React, Vue). Не подвержен CSRF-атакам. | Уязвим к **XSS-атакам** (если хакер внедрит вредоносный скрипт, он легко украдет токен через `localStorage.getItem()`). | Очищать пользовательский ввод, использовать CSP (Content Security Policy). |
| **HttpOnly Cookies** | JavaScript **не имеет доступа** к cookie. XSS-скрипты не могут украсть токен! | Уязвимы к **CSRF-атакам** (межсайтовая подделка запроса). | Использовать флаги `SameSite=Strict` или `SameSite=Lax`, а также `Secure` (только по HTTPS). |

> **Рекомендуемый стандарт безопасности:**
> Хранить **Access Token** в памяти приложения (JS variable) или Secure HttpOnly Cookie, а **Refresh Token** — строго в **HttpOnly, Secure, SameSite Cookie**. Передача данных должна происходить **исключительно по HTTPS**!

## 7. Концепция Access Token + Refresh Token

Так как JWT является stateless (сервер не хранит сессии в БД), **JWT нельзя легко заблокировать/отозвать до наступления `exp`**. Если токен украдут, хакер сможет пользоваться им до окончания срока действия.

Для решения этой проблемы используется пара токенов:

```text
 +------------------------------------------------------------------------+
 |                              ACCESS TOKEN                              |
 +------------------------------------------------------------------------+
 |  • Назначение: Доступ к защищенным API (эндпоинтам).                   |
 |  • Время жизни: КОРОТКОЕ (5 - 15 минут).                                |
 |  • Хранение: Память приложения / LocalStorage / Cookie.                |
 |  • Тип: JWT (Stateless).                                               |
 +------------------------------------------------------------------------+

 +------------------------------------------------------------------------+
 |                             REFRESH TOKEN                              |
 +------------------------------------------------------------------------+
 |  • Назначение: Получение новой пары (Access + Refresh) токенов.       |
 |  • Время жизни: ДОЛГОЕ (7 - 30 дней).                                   |
 |  • Хранение: Strictly HttpOnly, Secure Cookie (или база Redis).        |
 |  • Тип: Обычная случайная строка (Opaque string) или JWT (Stateful).   |
 +------------------------------------------------------------------------+
```

### Поток работы (Authentication Flow)

```text
[ Клиент ]                                                    [ Сервер ]
    |                                                             |
    |---- 1. POST /login (логин + пароль) ----------------------->|
    |<--- 2. Возвращает Access Token (10 мин) + Refresh Cookie ---|
    |                                                             |
    |---- 3. GET /api/user (Header: Authorization Bearer) ------->|
    |<--- 4. Данные пользователя (200 OK) ------------------------|
    |                                                             |
    |  ... проходит 10 минут, Access Token истек (exp) ...        |
    |                                                             |
    |---- 5. GET /api/user (с истекшим Access Token) ------------>|
    |<--- 6. Ошибка 401 Unauthorized -----------------------------|
    |                                                             |
    |---- 7. POST /refresh (отправляет Refresh Cookie) ---------->|
    |        (Сервер проверяет Refresh Token в своей БД/Redis)    |
    |<--- 8. Новая пара: Access Token + Refresh Token ------------|
    |                                                             |
    |---- 9. Повторный запрос GET /api/user --------------------->|
    |<--- 10. Успешный ответ (200 OK) ----------------------------|
```

### Что дает такая схема?

1. Если украдут **Access Token**, хакер сможет использовать его максимум 5–10 минут.
2. Когда пользователь нажимает «Выйти из всех устройств», сервер удаляет **Refresh Token** из своей базы. При попытке обновления клиент получит отказ, и сессия завершится.

## 8. Практический пример на Python (`PyJWT`)

Пример создания, подписи и валидации токена на языке Python.

```python
import jwt
import datetime

# 1. Секретный ключ (для алгоритма HS256)
SECRET_KEY = "my-super-secret-key-change-in-production"

# 2. Формируем Payload (полезную нагрузку)
payload = {
    "sub": "user_98765",                           # ID пользователя
    "name": "Алексей",                              # Имя
    "role": "editor",                              # Роль
    "iat": datetime.datetime.utcnow(),             # Время создания
    "exp": datetime.datetime.utcnow() + datetime.timedelta(minutes=15) # Истекает через 15 мин
}

# 3. Генерируем JWT Token
encoded_jwt = jwt.encode(payload, SECRET_KEY, algorithm="HS256")
print(f"Сгенерированный JWT:
{encoded_jwt}
")

# --- На стороне микросервиса (Проверка токена) ---

try:
    # 4. Декодируем и валидируем подпись и срок жизни (exp)
    decoded_payload = jwt.decode(
        encoded_jwt, 
        SECRET_KEY, 
        algorithms=["HS256"] # Явно указываем разрешенный алгоритм!
    )
    print("Токен валиден! Данные из токена:")
    print(decoded_payload)

except jwt.ExpiredSignatureError:
    print("Ошибка: Срок действия токена истек (exp)!")
except jwt.InvalidTokenError:
    print("Ошибка: Недействительный токен или неверная подпись!")
```

## 9. Чек-лист безопасности (Best Practices)

* [x] **Используйте HTTPS:** Всегда передавайте токены по зашифрованному каналу TLS/HTTPS.
* [x] **Задавайте короткий `exp`:** Access токен должен жить от 5 до 15 минут.
* [x] **Проверяйте `alg` на сервере:** Явно ограничивайте список допустимых алгоритмов подписи, запрещайте `alg: "none"`.
* [x] **Не храните секреты в Payload:** Никаких паролей, API-ключей и персональных данных.
* [x] **Используйте RS256 в больших системах:** Чтобы не передавать секретный ключ во все микросервисы.
* [x] **Защищайте Refresh токены:** Храните их в `HttpOnly, Secure, SameSite=Strict` Cookie.

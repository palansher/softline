## 1. Что такое Apache Kafka?

**Apache Kafka** — это распределенная платформа потоковой передачи событий (*Event Streaming Platform*) с высокой пропускной способностью, низкой задержкой и встроенной отказоустойчивостью.

В отличие от традиционных брокеров сообщений (RabbitMQ, ActiveMQ), Kafka функционирует как **распределенный распределяемый журнал записей (Append-Only Log)**, где сообщения не удаляются сразу после чтения, а хранятся в течение заданного времени (*retention policy*).

## 2. Базовые компоненты архитектуры

### 2.1. Брокер и Кластер (Broker & Cluster)

- **Kafka Broker (Брокер)** — отдельный сервер/узел с запущенным процессом Kafka. Отвечает за прием, хранение, репликацию и выдачу сообщений.
- **Kafka Cluster (Кластер)** — группа объединенных брокеров, работающих совместно. Кластер обеспечивает горизонтальное масштабирование и высокую доступность (*High Availability*).

#### Управление кластером и Контроллер (Controller)

- **Контроллер (Active Controller)** — один из брокеров кластера, выполняющий административные функции: отслеживает состояние узлов, координирует выборы Лидеров для партиций и управляет метаданными.
- **Эволюция консенсуса:**
  - *Legacy (ZooKeeper mode):* Метаданные и выборы контроллера управлялись внешним ансамблем Apache ZooKeeper.
  - *Modern (KRaft mode — Kafka Raft):* Начиная с Kafka 3.3+ (и как единственный стандарт в 4.0+), Kafka использует встроенный протокол консенсуса **KRaft**. ZooKeeper больше не требуется, а роль контроллеров выполняют специально выделенные брокеры кластера.

### 2.2. Топики, Партиции и Оффсеты

```
TOPIC: "payment-events"
┌──────────────────────────────────────────────────────────────┐
│ Partition 0:  [Offset 0] [Offset 1] [Offset 2] [Offset 3]... │
├──────────────────────────────────────────────────────────────┤
│ Partition 1:  [Offset 0] [Offset 1] [Offset 2]...            │
├──────────────────────────────────────────────────────────────┤
│ Partition 2:  [Offset 0] [Offset 1] [Offset 2] [Offset 3]... │
└──────────────────────────────────────────────────────────────┘
```

1. **Топик (Topic)** — логический поток или категория сообщений (например, `user-registrations`, `order-events`).
2. **Партиция (Partition)** — физический сегмент топика. Топик делится на 1 и более партиций, распределяемых по разным брокерам кластера.
   - **Балансировка:** Партиционирование позволяет параллелить запись и чтение.
   - **Гарантия порядка:** **Порядок сообщений гарантируется СТРОГО внутри одной партиции**, но НЕ между разными партициями одного топика.
3. **Смещение (Offset)** — монотонно возрастающий целочисленный идентификатор сообщения внутри конкретной партиции (начиная с `0`). Оффсет уникален в рамках партиции, но повторяется в других партициях.

## 3. Анатомия события (Message / Record)

Каждое сообщение в Kafka состоит из следующих полей:

| Поле | Описание | Обязательность |
| :--- | :--- | :--- |
| **Key (Ключ)** | Используется для определения партиции, в которую попадет сообщение. Вычисляется через хэш-функцию (`murmur2(key) % partitions_count`). Все сообщения с одинаковым ключом гарантированно попадают в одну партицию и обрабатываются в строгом хронологическом порядке. | Опционально |
| **Value (Значение)** | Полезная нагрузка (*Payload*). Может быть в формате JSON, Avro, Protobuf, String, Raw Bytes. | Опционально |
| **Headers (Заголовки)** | Набор метаданных в формате «ключ-значение» (например, `trace_id`, `content-type`, `source_system`). | Опционально |
| **Timestamp (Штамп времени)** | Время создания сообщения (`CreateTime`) или время записи в логи брокера (`LogAppendTime`). | Автоматически |

Да, это может показаться неожиданным, но **сообщение со значением `null` (пустым `Value`) — это полностью штатная, валидная и активно используемая фича в Kafka**. Брокер без проблем примет такое сообщение и запишет его в партицию.

Более того, возможность отправки `null` в `Value` имеет критическое значение для работы системы.

---

### Зачем нужны сообщения с пустым `Value`?

#### 1. Удаление данных (Tombstone-сообщения)

Это главный вариант использования. В Kafka есть механизм очистки старых сообщений, который называется **Log Compaction** (уплотнение лога).

В топиках с включенным уплотнением (`cleanup.policy=compact`) Kafka хранит только *последнее* известное состояние для каждого ключа.

- Если вам нужно **удалить** ключ из системы (например, пользователь удалил свой аккаунт или запись в БД была стёрта), продюсер отправляет сообщение вида:
- `Key`: `"user_123"`
- `Value`: `null`

- Такое сообщение с `Value = null` называется **Tombstone** («надгробный камень»).
- Когда брокер и консьюмеры видят Tombstone, они понимают: *«Запись с ключом `user_123` помечена на удаление»*. Брокер сохраняет этот маркер на некоторое время (настраивается через `delete.retention.ms`), чтобы консьюмеры успели прочитать факт удаления, а затем физически удаляет все записи с этим ключом из диска.

#### 2. Сигнальные события (Signal / Event-only)

Иногда сам факт наступления события (в сочетании с ключом, заголовками или меткой времени) уже содержит всю необходимую информацию, и передавать полезную нагрузку в `Value` просто не требуется.

- **Пример:** Событие `UserLoggedOut`.
- `Key`: `"user_456"`
- `Headers`: `{"device": "mobile_ios"}`
- `Value`: `null`
- Консьюмеру достаточно знать, кто именно и когда вышел, тело сообщения здесь избыточно.

---

### Разница между `null` и пустой строкой (`""`)

В Kafka важно различать два понятия:

| Состояние | Поведение в Kafka |
| --- | --- |
| **`Value = null`** | Маркер отсутствия значения (Tombstone). Используется для удаления ключей при Log Compaction. |
| **`Value = b""`** *(массив байт нулевой длины)* | Сообщение **содержит** значение, но оно пустое. Это **НЕ** Tombstone. Такое сообщение НЕ удалит ключ при уплотнении лога. |

---

### Итог по обязательности полей

- **Key:** Опционален. Если `null` — сообщения распределяются по партициям через Round-Robin / Sticky Partitioning.

- **Value:** Опционален. Если `null` — сообщение служит маркером удаления (Tombstone) или простым сигналом.

- **Headers:** Опциональны. Могут быть пустыми.

Следовательно, минимально валидное сообщение в Kafka может состоять буквально из `null`-ключевых данных и временной метки, которую брокер проставит автоматически.

## 4. Репликация и Отказоустойчивость

Для предотвращения потери данных каждая партиция реплицируется на несколько брокеров (*Replication Factor*).

```
Topic: orders, Partition 0, Replication Factor = 3
┌───────────────────────┐   Fetch/Sync   ┌───────────────────────┐
│ Broker 1 (LEADER)     │ <───────────── │ Broker 2 (FOLLOWER)   │
│ Writes & Reads        │                └───────────────────────┘
│                       │   Fetch/Sync   ┌───────────────────────┐
│                       │ <───────────── │ Broker 3 (FOLLOWER)   │
└───────────────────────┘                └───────────────────────┘
```

- **Leader Replica (Лидер):** Главная реплика партиции. Все операции записи (от Producer) и, как правило, чтения (от Consumer) проходят через Лидера.
- **Follower Replica (Фолловер):** Пассивная реплика. В фоновом режиме дублирует (асинхронно вычитывает) записи с Лидера.
- **ISR (In-Sync Replicas):** Множество реплик (включая Лидера), которые «успевают» за Лидером без критических задержек. Только узел из группы ISR может быть выбран новым Лидером при падении текущего.

### Настройки подтверждения записи (Producer `acks`)

- `acks=0` (*Fire-and-forget*): Продюсер не ждет подтверждения. Максимальная скорость, высокий риск потери данных.
- `acks=1`: Продюсер ждет подтверждения **только от Лидера**. Средняя надежность.
- `acks=all` (или `acks=-1`): Продюсер ждет, пока запись будет подтверждена Лидером и **всеми синхронными репликами (ISR)**. В сочетании с `min.insync.replicas=2` обеспечивает максимальную защиту от потери данных.

## 5. Консьюмеры и Группы Консьюмеров (Consumer Groups)

**Consumer Group (Группа подписчиков)** — механизм масштабирования чтения.

```
Partition 0 ───> Consumer A ┐
Partition 1 ───> Consumer B ├── Consumer Group "analytics-service"
Partition 2 ───> Consumer C ┘
```

### Фундаментальные правила

1. Каждая партиция внутри одной группы обрабатывается **строго одним консьюмером**.
2. Один консьюмер может читать из нескольких партиций одновременно.
3. Если число консьюмеров в группе **превышает** число партиций в топике, избыточные консьюмеры будут **простаивать** (*Idle*).
4. Разные группы консьюмеров читают один и тот же топик независимо друг от друга.

### Сохранение прогресса (Offsets Commit)

Консьюмеры сохраняют текущую позицию чтения (*Offset*) в специальный системный топик `__consumer_offsets`.

- **Auto-commit (`enable.auto.commit=true`):** Периодическое автоматическое сохранение. Проще, но повышает риск дублирования при аварийном завершении.
- **Manual commit:** Ручное подтверждение после успешной бизнес-обработки сообщения (синхронное или асинхронное).

## 6. Гарантии доставки (Delivery Semantics)

| Гарантия | Описание | Механизм реализации | Потеря данных | Дубликаты | Скорость |
| :--- | :--- | :--- | :---: | :---: | :---: |
| **At-most-once**<br>*(Максимум 1 раз)* | Сообщение либо обработано один раз, либо потеряно. Повторов нет. | `acks=0` или фиксация оффсета *до* обработки бизнес-логики. | **Да** | **Нет** | Высокая |
| **At-least-once**<br>*(Минимум 1 раз)* | Сообщение гарантированно будет обработано, но возможны повторы (дубли). | `acks=all` + повторные отправки при сбоях (*retries*) + фиксация оффсета *после* обработки. | **Нет** | **Да** | Средняя |
| **Exactly-once (EOS)**<br>*(Ровно 1 раз)* | Гарантируется доставка и обработка строго один раз без потерь и дублей. | Idempotent Producer (`enable.idempotence=true`) + Transactional API (`transactional.id`) + Read Committed Consumer. | **Нет** | **Нет** | Ниже |

## 7. Способы отправки сообщений (Producer Methods)

1. **Fire-and-forget (Отправил и забыл):**

   ```python
   producer.send('my_topic', value=b'data')
   # Ошибки сети или сбои брокера игнорируются
   ```

2. **Synchronous Send (Синхронная отправка):**

   ```python
   future = producer.send('my_topic', value=b'data')
   record_metadata = future.get(timeout=10) # Блокирует поток до получения ACK
   ```

3. **Asynchronous Send with Callback (Асинхронная отправка с обратным вызовом):**

   ```python
   def on_send_success(record_metadata):
       print(f"Recorded to {record_metadata.topic} [{record_metadata.partition}]")

   def on_send_error(ex):
       logger.error("Failed to send", exc_info=ex)

   producer.send('my_topic', value=b'data').add_callback(on_send_success).add_errback(on_send_error)
   ```

## 8. Экосистема Apache Kafka

### 8.1. Kafka Connect

Фреймворк для интеграции Kafka с внешними системами без написания пользовательского кода:

- **Source Connector:** Непрерывно импортирует данные из внешних источников (PostgreSQL, MySQL, MongoDB, S3) в топики Kafka.
- **Sink Connector:** Непрерывно экспортирует данные из топиков Kafka во внешние хранилища (Elasticsearch, ClickHouse, Snowflake, PostgreSQL).

### 8.2. Stream Processing (Kafka Streams & ksqlDB)

- **Kafka Streams:** Клиентская Java-библиотека для построения высоконагруженных приложений потоковой обработки (фильтрация, трансформация, агрегация, соединения `join` потоков).
- **ksqlDB / KSQL:** Событийно-ориентированный SQL-движок, позволяющий выполнять сложные потоковые преобразования над топиками Kafka с помощью декларативных SQL-запросов (без написания кода на Java/Python).
